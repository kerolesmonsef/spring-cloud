WSO2 API Manager — Study Notes

How a plain Spring Boot backend becomes a managed, gateway-fronted API: publish it, subscribe an app to it, mint a token, call it. Continuation file for wso2/todo.md — read this before the next session, update it after.

01 What problem this solves

An API gateway sits between callers and a backend so the backend never faces the internet directly. WSO2 API Manager is a full API management layer built on top of that idea — not just routing (that's LoadBalancer/ in this repo) and not just service lookup (that's ServiceDiscovery/'s Eureka). It adds a lifecycle for the API itself, a self-service catalog for consumers, and OAuth2-based access control in front of the plain backend.

Reach for WSO2 AM over Spring Cloud Gateway or a bare Nginx proxy when you need the governance/monetization/analytics side — API lifecycle, subscriber self-service, throttling tiers, per-scope authorization — not just lightweight request routing.

03 Backend → live API, step by step

Everything downstream of the gateway is one substitution: a caller hits gatewayHost/<context>/<version>/* and WSO2 forwards whatever's after the version straight onto endpoint/*.

mbank.com/hello → (client calls) wso2domain.com/<context>/<version>/hello → (gateway proxies) <endpoint>/hello
1
Publisher Create the API

REST API from scratch: Name, Context (the path segment after the gateway host), Version (start 1.0.0), Endpoint = your real backend base URL. Example used here: WSO2LearningAPI, context /wso2learn, endpoint http://localhost:8092.

2
Publisher Check the resources

"From Scratch" defaults to one wildcard resource — /* with every method (GET/PUT/POST/DELETE/PATCH) — which is why any backend path works with zero mapping. To scope down to your real paths (e.g. expose only GET /items/{id}), go to Develop → Resources, not Overview — Overview is a read-only summary and won't let you edit anything.

Gotcha — Overview and Resources are separate sub-tabs. Overview just prints whatever resources already exist (e.g. that lone /*). To split it into explicit rows like GET /hello and GET /items/{id}, delete the wildcard row inside the Resources editor and add the real ones — only then does a per-resource scope selector appear.
3
Publisher Publish

Lifecycle: Created → Published. Unpublished APIs never appear in DevPortal, regardless of how the resources are configured.

4
DevPortal Pick an application

Applications (top nav) → use the built-in DefaultApplication or create your own. An application holds keys and subscriptions — it isn't tied to one API, so the same app can subscribe to many.

5
DevPortal Subscribe the app to the API

APIs → open the API → Subscriptions tab → pick the application → Subscribe. This is the actual authorization gate — a technically valid token from an unsubscribed app still gets rejected at the gateway.

6
DevPortal Generate keys

Inside the application → Sandbox Keys (Production Keys is a separate credential set) → Generate Keys → Consumer Key + Consumer Secret. These identify the application, not any one subscription.

7
DevPortal Generate an access token

Same screen → Generate Access Token. Under the hood this is a client_credentials grant: POST https://localhost:9443/oauth2/token, Basic-authed with the consumer key/secret. Token is short-lived — 1 hour by default — copy it now.

8
Test Call it through the gateway

API's Overview tab has the invoke URL — copy it, append the resource path, call with Authorization: Bearer <token> from Postman/curl.

Gotcha — steps 6/7 (keys, token) don't strictly have to come after step 5 (subscribe) — WSO2 lets you generate both first. But the token is dead weight against this API until the subscription exists: authorization is checked at the subscription level, not just token validity/signature.

06 Notes & gotchas log

Wildcard resource is the default, not a fallback.

"From Scratch" always starts you on one /* resource covering every HTTP method. It's easy to mistake this for "WSO2 auto-detected my two endpoints" — it didn't; it just proxies everything through unfiltered until you replace it.

Overview ≠ the resource editor.

Develop → Overview is a read-only summary card. The actual add/edit/delete UI for resources is its own sub-tab (Resources / API Definition, exact label varies by build). Scope selectors only show up per-row inside that editor, never on the Overview summary.

Keys are per-application; the subscription is the real gate.

A consumer key/secret pair — and the token it produces — belongs to the application, not to any single API. WSO2 will happily hand out a valid token for an app that isn't subscribed to anything; the gateway rejects it at call time, not at token-issue time.

Token endpoint, unwrapped.

"Generate Access Token" in DevPortal is a thin UI over POST https://localhost:9443/oauth2/token, grant_type=client_credentials, consumer key/secret as HTTP Basic auth. Same call is scriptable directly with curl once the keys exist — the DevPortal button isn't the only way to get one.

Sandbox vs. Production keys are separate credential sets.

Generating Sandbox keys doesn't also produce Production ones — they're independent Consumer Key/Secret pairs under the same application, presumably gated to different environments/gateways in a real deployment.

admin/admin kept deliberately.

Default Carbon credentials were left unchanged — this is a local learning box only, not a decision to carry into anything shared or production-facing.
