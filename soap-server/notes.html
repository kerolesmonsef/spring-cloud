SOAP Review Notes

Quick mind-bookmarks only. Not a tutorial — see todo.md for that.

Rule of thumb (XSD)

  • Everything used as a request/response/DTO must exist in the .xsd first. XSD = contract. Java classes (wsdl/request/response) mirror it, not the other way round. Example: UserEndpoint#getUser takes GetUserRequest — XSD first, Java mirror second (users.xsd): 
    <xs:element name="getUserRequest">
    <xs:complexType>
        <xs:sequence>
            <xs:element name="id" type="xs:long"/>
        </xs:sequence>
    </xs:complexType>
</xs:element>
    Java mirror (user/request/GetUserRequest.java) — same element name, same field: 
    @Data
@XmlRootElement(name = "getUserRequest")
public class GetUserRequest {
    private long id;
}
    Response side, XSD (getUserResponse) then Java (user/response/GetUserResponse.java): 
    <xs:element name="getUserResponse">
    <xs:complexType>
        <xs:sequence>
            <xs:element ref="tns:user" minOccurs="0"/>
        </xs:sequence>
    </xs:complexType>
</xs:element>
    @Data
@XmlRootElement(name = "getUserResponse")
@XmlAccessorType(XmlAccessType.FIELD)
public class GetUserResponse {
    @XmlElement(name = "user")
    private UserXml user;
}
    Mapping: ref="tns:user" minOccurs="0" → single nullable UserXml user field (null = element omitted). Endpoint uses both: 
    @PayloadRoot(namespace = NAMESPACE, localPart = "getUserRequest")
@ResponsePayload
public GetUserResponse getUser(@RequestPayload GetUserRequest request) { ... }
  • XSD holds two kinds of tags:
    • xs:complexType — the shape (fields, order). Named = reusable (ref=), anonymous = one-off. Example: named user type (reused by get/list/create responses) vs anonymous type inside getUserRequest (one-off): 
      <xs:complexType name="user">          <!-- named: reusable -->
    <xs:sequence>
        <xs:element name="id" type="xs:long"/>
        <xs:element name="name" type="xs:string"/>
        <xs:element name="email" type="xs:string"/>
    </xs:sequence>
</xs:complexType>
      Java mirror: @XmlType(name = "user") public class UserXml (user/wsdl/UserXml.java).
    • xs:element — the nameable tag pluggable into a type. Example: user element wraps the user type so other types can ref it: 
      <xs:element name="user" type="tns:user"/>
...
<xs:element ref="tns:user" minOccurs="0" maxOccurs="unbounded"/>   <!-- in listUsersResponse -->
  • Per CRUD op: 1 request element + 1 response element. Named type only when shape reused (e.g. user). Example: deleteUserRequest + deleteUserResponse in users.xsd; only user is a named type because 3 responses share it. Endpoint pair: DeleteUserRequest in → DeleteUserResponse out.

Types allowed inside XSD

  • Primitives: xs:string xs:long xs:int xs:boolean xs:dateTime xs:date xs:decimal Used here: xs:long → Java long id (getUserRequest, user); xs:string → String name/email; xs:boolean → success in updateUserResponse/deleteUserResponse. Not used yet: int, dateTime, date, decimal.
  • Structure: xs:sequence (ordered), xs:choice, xs:all Used here: only xs:sequence — updateUserRequest must send id, name, email in that order, else schema-invalid: 
    <xs:sequence>
    <xs:element name="id" type="xs:long"/>
    <xs:element name="name" type="xs:string"/>
    <xs:element name="email" type="xs:string"/>
</xs:sequence>
  • Cardinality: minOccurs, maxOccurs="unbounded" Example: getUserResponse → minOccurs="0" (user may be absent) → Java single UserXml, null if not found. listUsersResponse → maxOccurs="unbounded" → Java List<UserXml> user = new ArrayList<>(). createUserResponse → default 1..1 → always set.
  • Validation only (no logic): xs:pattern, xs:minLength, xs:enumeration — not used yet in users.xsd Would go on createUserRequest's email — see "Validation in XSD" below for the snippet.

users.xsd review

  • 1 shared type: user (id, name, email) Example: getUserResponse, listUsersResponse, createUserResponse all ref="tns:user"; Java side all use UserXml, filled by UserEndpoint.toXml(User) (JPA entity → wire DTO, entity never exposed).
  • 5 ops: get / list / create / update / delete — each own request+response Example: 5 @PayloadRoot methods in UserEndpoint, localPart = getUserRequest, listUsersRequest, createUserRequest, updateUserRequest, deleteUserRequest.
  • createUserRequest has no id (server-assigned) Example: request carries only name+email; id comes back in the response: 
    response.setUser(toXml(userService.create(request.getName(), request.getEmail())));
  • update/deleteResponse → just success: boolean, no object returned Example: UserService.delete(id) returns false if !existsById, else deletes and returns true; endpoint does response.setSuccess(userService.delete(request.getId())). Same for update.
  • listUsersRequest → empty complexType (no fields, just a marker) Example: XSD <xs:element name="listUsersRequest"><xs:complexType/></xs:element> ↔ Java, empty class, no fields, no Lombok: 
    @XmlRootElement(name = "listUsersRequest")
public class ListUsersRequest {
}

REST vs SOAP annotation mapping

REST (Spring MVC)SOAP (Spring-WS)Role
@RestController@Endpointrequest handler bean
@RequestMapping/@PostMapping("/path")@PayloadRoot(namespace, localPart)routing (URL+verb vs XML namespace+element name)
@RequestBody@RequestPayloaddeserialize incoming body
@ResponseBody (implicit)@ResponsePayloadserialize return value

REST: many URLs, routed by path+verb. SOAP: one URL (/ws), always POST, routed by which <xxxRequest> element sits inside <soap:Body>.

Example: all four annotations together in this repo (UserEndpoint). REST equivalent: @GetMapping("/users/{id}") + @PathVariable.

@Endpoint                                                        // ~ @RestController
public class UserEndpoint {
    private static final String NAMESPACE = "http://keroles.com/soapserver/users";

    @PayloadRoot(namespace = NAMESPACE, localPart = "getUserRequest") // ~ @PostMapping("/path")
    @ResponsePayload                                                  // ~ @ResponseBody
    public GetUserResponse getUser(@RequestPayload GetUserRequest request) { // ~ @RequestBody
        ...
    }
}

Wire (what the client POSTs to /ws, routes to getUser because of the element inside <soap:Body>):

<soapenv:Envelope xmlns:soapenv="http://schemas.xmlsoap.org/soap/envelope/"
                  xmlns:us="http://keroles.com/soapserver/users">
  <soapenv:Body>
    <us:getUserRequest>
      <us:id>1</us:id>
    </us:getUserRequest>
  </soapenv:Body>
</soapenv:Envelope>

Servlet mapping that makes it "one URL": WebServiceConfig registers MessageDispatcherServlet on "/ws/*".

New SOAP API checklist (with examples from this repo)

Worked example throughout: adding a new op searchUsersByName to the existing users domain (no new namespace needed — see step 3).

  • 1. XSD — add request/response elements. Contract first, in users.xsd: 
    <xs:element name="searchUsersByNameRequest">
  <xs:complexType>
    <xs:sequence>
      <xs:element name="name" type="xs:string"/>
    </xs:sequence>
  </xs:complexType>
</xs:element>
<xs:element name="searchUsersByNameResponse">
  <xs:complexType>
    <xs:sequence>
      <xs:element ref="tns:user" minOccurs="0" maxOccurs="unbounded"/>
    </xs:sequence>
  </xs:complexType>
</xs:element>
    Named type = reusable (ref="tns:user"). Per op: 1 request + 1 response element. Note: this xsd is not consumed by any xjc/codegen plugin in this repo (check build.gradle — only wsdl4j + jaxb-runtime, no generator) — it's contract documentation + WSDL schema source. Java DTOs below are hand-written to match it.
  • 2. Java DTOs — hand-write request/response classes. 
    // request/SearchUsersByNameRequest.java
@Data
@XmlRootElement(name = "searchUsersByNameRequest")
public class SearchUsersByNameRequest {
    private String name;
}

// response/SearchUsersByNameResponse.java
@Data
@XmlRootElement(name = "searchUsersByNameResponse")
public class SearchUsersByNameResponse {
    private List<UserXml> user = new ArrayList<>();
}
  • 3. Namespace check — reuse, don't duplicate. request/package-info.java already declares: 
    @XmlSchema(
    namespace = "http://keroles.com/soapserver/users",
    elementFormDefault = XmlNsForm.QUALIFIED)
package com.keroles.soapserver.user.request;
    New classes in same package inherit it automatically — no per-class namespace needed. Separate domain (e.g. posts) → separate package + own package-info.java + own namespace + own NAMESPACE constant in its endpoint (a single @Endpoint class can mix namespaces per-method via @PayloadRoot, but cleaner to split by domain — see PostEndpoint.java). Three copies of the same namespace string must stay in sync by hand: package-info.java, xsd targetNamespace, endpoint's NAMESPACE constant — nothing enforces this at compile time.
  • 4. Endpoint method — route by namespace + localPart. 
    @PayloadRoot(namespace = NAMESPACE, localPart = "searchUsersByNameRequest")
@ResponsePayload
public SearchUsersByNameResponse searchUsersByName(@RequestPayload SearchUsersByNameRequest request) {
    SearchUsersByNameResponse response = new SearchUsersByNameResponse();
    userService.findByNameContaining(request.getName()).forEach(user -> response.getUser().add(toXml(user)));
    return response;
}
    localPart must equal the request's @XmlRootElement(name=...) exactly — mismatch here 404s even if namespace is right. Routing key = XML element name inside <soap:Body>, not URL.
  • 5. Service logic. Add findByNameContaining(String name) to UserService, backed by a repo query. Business logic lives here, not in the endpoint.
  • 6. WSDL sanity check. Restart, hit /ws/users.wsdl — new elements should appear automatically since the WSDL bean (WebServiceConfig.java) points at users.xsd as its schema source: 
    @Bean(name = "users")
public DefaultWsdl11Definition defaultWsdl11Definition(XsdSchema usersSchema) {
    DefaultWsdl11Definition d = new DefaultWsdl11Definition();
    d.setPortTypeName("UsersPort");
    d.setLocationUri("/ws");
    d.setTargetNamespace("http://keroles.com/soapserver/users");
    d.setSchema(usersSchema);
    return d;
}
    Bean name "users" → WSDL served at /ws/users.wsdl. If new elements don't show up here, xsd wasn't saved/picked up — check before debugging the endpoint.

Other gaps (not part of the add-an-op checklist)

  • Validation in XSD, not code. Missing in users.xsd — no xs:pattern/minLength. Real API: constrain in the schema itself, e.g. xs:pattern value=".+@.+" on email, so bad input is rejected before it hits endpoint code. Example: today createUserRequest.email is plain xs:string, so email="abc" is saved as-is by UserService.create. Fix (XSD only, no Java change): 
    <xs:element name="email">
    <xs:simpleType>
        <xs:restriction base="xs:string">
            <xs:pattern value=".+@.+"/>
        </xs:restriction>
    </xs:simpleType>
</xs:element>
    Caveat: Spring-WS only enforces the schema if a PayloadValidatingInterceptor is registered — none is in WebServiceConfig yet, so add one or the pattern is documentation only.
  • SOAP faults. Not present here — getUser with bad id just returns a response with no user set (silent, not prod-grade). Add @SoapFault on a thrown exception, or a SoapFaultMappingExceptionResolver bean, so errors come back as proper SOAP faults. Example: current UserEndpoint.getUser — unknown id yields an empty <getUserResponse/>; same for updateUser/deleteUser, which report only success=false: 
    userService.findById(request.getId()).ifPresent(user -> response.setUser(toXml(user)));
return response;   // not found → empty response, no fault
  • Versioning. Contract change (new required field etc.) → new namespace or new XSD version. Old clients are bound tight to the WSDL they first read. Example: making user require a new phone field would break every client. Instead publish http://keroles.com/soapserver/users/v2: new targetNamespace in the xsd, new package-info.java, new NAMESPACE constant. (Existing model: users vs posts already split by namespace, posts.xsd + PostEndpoint.)
  • Security. Not present here. WS-Security (Wss4jSecurityInterceptor bean) for signing/encryption, or simpler: HTTPS + basic-auth interceptor in front of /ws/*. Example: WebServiceConfig.messageDispatcherServlet maps /ws/* with no auth — anyone can call deleteUserRequest. Hook point: add the interceptor via a WsConfigurerAdapter.addInterceptors bean, or filter /ws/* in a servlet filter.
