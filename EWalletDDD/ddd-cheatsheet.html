Domain-Driven Design · EWalletDDD Quick Reference

EWalletDDD, mapped to folders

Subject: this actual repo — com.keroles.ewalletddd, 5 bounded contexts, MySQL-backed. Where ddd/ddd-cheatsheet.html maps DDD vocabulary to a generic wallet, this sheet maps it to the code that's actually on disk. Source of truth for details: EWalletDDD/DDD-STUDY.md.

The four words, and which ones are folders

Word What it is A folder? In EWalletDDD
Domain The whole business problem No — it's the whole app “a digital wallet for stablecoins”
Subdomain A slice of the business: Core / Supporting / Generic No — a classification, a way to think Accounting is Core (only one Keroles labeled explicitly); Transfer read as Core too — both move real balances. Cashout/Topup read as Supporting — rail orchestration around the ledger. Pricing reads as Generic — a config-driven fee calculator, the kind of thing you could buy off the shelf.
Bounded Context A boundary where one model is valid Yes — your top-level folder accounting, cashout, topup, transfer, pricing
Aggregate A cluster guarded by one root Entity Yes — a folder inside a context Account, CashoutRequest, TopupRequest, Transfer

Folder structure — com.keroles.ewalletddd

  • Core
  • Supporting
  • Generic
  • PORT = interface
  • ACL = anticorruption adapter (only class allowed to import the other context)
  • com.keroles.ewalletddd
    • shared.domain — no context, just shared value objects
      • Money.java — VO, non-negative, fixed 2dp scale
      • Currency.java — VO wrapping a code, deliberately NOT java.util.Currency (that's ISO-4217 fiat-only; BTC/ETH/SOL would throw)
      • UserId.java
    • accounting — Bounded Context (Core) tables a_*
      • domain.model
        • Account.java — Aggregate Root; verbs deposit/withdraw/hold/settle/release, no setters
        • Transaction.java — Aggregate Root; nested Entry/Transfer/Type/Status/Direction
        • User.java — minimal aggregate, id+createdAt only; Onboarding will own the rich User
      • domain.valueObject
        • AccountId, TransactionId
        • AccountReference — static FEE/VAT well-known accounts
        • AccountType — SYSTEM/USER/EXTERNAL/FEE/VAT
        • Party — a tx endpoint: reference + AccountType
      • domain.event AccountOpenedEvent, MoneyDepositedEvent, MoneyWithdrawnEvent, FundsHeldEvent, FundsSettledEvent, FundsReleasedEvent
      • domain.repository — PORT AccountRepository, TransactionRepository, UserRepository
      • application — the ONLY door other contexts may call
        • AccountApplicationService — lifecycle+queries: openAccount, getAccount
        • TransactionApplicationService — topup / transfer / cashout / settle / release
      • infrastructure.persistence — entity / mapper / repository(SpringData) / adapter, Option B save (dirty-check on a managed entity, @Version optimistic lock)
      • infrastructure.reference — AccountType/Currency seed rows, repo-only CommandLineRunner, no aggregate — the one sanctioned "infra talks straight to infra" exception
      • presentation AccountController (open/get/topup/transfer — cashout/settle/release are NOT public REST)
    • cashout — Bounded Context (Supporting) tables c_*
      • domain.model CashoutRequest — state machine RESERVED→DISPATCHED→CONFIRMED/FAILED
      • domain.valueObject CashoutId, Rail (AANI/LULU/MBANK), LedgerAccountRef, LedgerReservationRef
      • domain.port — PORT CashoutRailPort, CashoutRailRegistry, LedgerAccountPort
      • application CashoutApplicationService — requestCashout → CashoutId, confirm(id), fail(id), get(id)
      • infrastructure.ledger LedgerAccountAdapter — ACL only cashout class importing accounting.*
      • infrastructure.rail AaniAdapter, LuLuAdapter, MbankAdapter (fakes) + SpringCashoutRailRegistry, self-assembles by Rail
      • presentation CashoutController
    • topup — Bounded Context (Supporting) tables t_*
      • domain.model TopupRequest — PENDING→COMPLETED/FAILED, deliberately NO hold: the money isn't the user's until the rail delivers it
      • domain.port — PORT TopupRailPort, LedgerTopupPort, TopupRailRegistry
      • application TopupApplicationService — requestTopup, confirm, fail, get
      • infrastructure.ledger LedgerTopupAdapter — ACL
      • infrastructure.rail TcsAdapter (async→PENDING), MbankAdapter (sync→CONFIRMED, bean "topupMbankAdapter" — cashout already owns the default MbankAdapter bean name)
      • presentation TopupController
    • transfer — Bounded Context (Core) tables tr_*
      • domain.model Transfer — NO state machine; constructed already-complete via complete(from,to,amount,holdRef,settleRef)
      • domain.valueObject TransferId, LedgerHoldRef, LedgerSettleRef, FeeLeg (Payer SENDER/RECEIVER × FeeTarget FEE/VAT × Money)
      • domain.port — PORT LedgerTransferPort (hold, settle-with-legs), PricingPort (calculateTransferFees → FeeQuote, this context's own ACL contract into Pricing)
      • application TransferApplicationService — ask Pricing for fees FIRST (fail before any hold exists), hold amount+senderFee+senderVat, build 4 FeeLegs, settle(hold, principal, legs), self-transfer guarded — one @Transactional call
      • infrastructure.ledger LedgerTransferAdapter — ACL only transfer class importing accounting.*
      • infrastructure.pricing PricingAdapter — ACL only transfer class importing pricing.*
      • presentation TransferController
    • pricing — Bounded Context (Generic) tables p_*
      • domain.valueObject TransactionType (own copy), FeeType (VALUE/PERCENTAGE), FeeChargeRule, FeeCalculationResult
      • domain.repository — PORT FeeChargeRepository (never empty — unconfigured type resolves to FeeChargeRule.zero())
      • domain.service FeeCalculationService — pure, no Spring; one strategy per TransactionType (Topup/Cashout/Transfer), shared math in FeeMath
      • application PricingApplicationService — calculateFees(type, amount), never throws
      • infrastructure.persistence — read-only, no @Version (config data, not an aggregate)
      • no presentation/ yet — nothing asked for a REST edge

Flow Direction Balance verbs Entries Status
topupsystem → usersystem.withdraw + user.deposit2 (system DEBIT, user CREDIT)COMPLETED, atomic

cashoutuser → systemuser.hold only1 (user DEBIT)PENDING

cashout / settle / release each run in ONE DB transaction — no double-spend. Transaction status guard IS the idempotency check (duplicate settle throws), proven by CashoutRejectAtDispatchTest / TopupDuplicateCallbackTest.

Architecture laws, condensed

  • Layers per context: domain/ (pure JDK, no Spring/JPA) · application/ (use cases, @Transactional, no business rules) · infrastructure/ (persistence, adapters) · presentation/ (controllers, DTOs).
  • Only the Application Service is exposed to other contexts — never the aggregate, domain service, or repository directly.
  • Business verbs, never setters. Events are raised inside the aggregate, pulled and published by the app service.
  • Repository save = Option B: adapter loads the managed JPA entity, copies domain state onto it → dirty checking does the UPDATE, @Version works, domain stays version-free.
  • Tables belong to ONE context, full stop — prefix (a_/c_/t_/tr_/p_) makes ownership visible in the schema itself; other contexts never SELECT them.
  • Idempotency = guarded state transitions on the aggregate (duplicate settle throws), not ifs in a controller.
  • Cross-context calls only through one ACL class per pair (ACL tag above) — keeps the future microservice split a matter of moving a package, not rewriting call sites.
  • Only Application Service and ValueObject are shareable across contexts — Aggregate, Entity, domain Service, Repository never cross a context boundary, not even read-only.
  • Always hexagonal: Ports & Adapters. Domain/Application define PORT interfaces; infrastructure/ supplies adapters (persistence, ledger, rail, pricing). Domain depends on nothing outward — adapters depend on the port, never reverse.
