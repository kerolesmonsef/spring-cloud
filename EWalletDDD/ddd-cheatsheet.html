Domain-Driven Design · EWalletDDD Quick Reference

EWalletDDD, mapped to folders

Subject: this actual repo — com.keroles.ewalletddd, 5 bounded contexts, MySQL-backed. Where ddd/ddd-cheatsheet.html maps DDD vocabulary to a generic wallet, this sheet maps it to the code that's actually on disk. Source of truth for details: EWalletDDD/DDD-STUDY.md.

The four words, and which ones are folders

Word What it is A folder? In EWalletDDD
Domain The whole business problem No — it's the whole app “a digital wallet for stablecoins”
Subdomain A slice of the business: Core / Supporting / Generic No — a classification, a way to think Accounting is Core (only one Keroles labeled explicitly); Transfer read as Core too — both move real balances. Cashout/Topup read as Supporting — rail orchestration around the ledger. Pricing reads as Generic — a config-driven fee calculator, the kind of thing you could buy off the shelf.
Bounded Context A boundary where one model is valid Yes — your top-level folder accounting, cashout, topup, transfer, pricing
Aggregate A cluster guarded by one root Entity Yes — a folder inside a context Account, CashoutRequest, TopupRequest, Transfer

Folder anatomy — what each folder should hold

The template every bounded context follows. Read it top-down: each folder says what goes in and what must stay out. Not every context needs every folder — create a folder only when its first file appears (○ optional marks the ones created on demand).

  • 📦 context root
  • 📁 folder
  • 📄 file
  • ■ domain
  • ■ application
  • ■ infrastructure
  • ■ presentation
  • 📦<context>/ — one bounded context, one model, one vocabulary (e.g. accounting)
    • 📁domain/ — the business. Pure JDK: NO Spring, NO JPA, NO Jackson annotations. Depends on nothing outward.
      • 📁model/ — Aggregate Roots + inner Entities. Business verbs (deposit, hold, settle), never setters. Raises events inside.
        • 📄Account.java
      • 📁valueObject/ — immutable, equal by value, self-validating (ids, Money, enums, refs). The ONLY domain type other contexts may share.
        • 📄AccountId.java AccountType.java
      • 📁event/ — domain events, past tense, immutable facts (MoneyDepositedEvent). Raised by the aggregate; published by the app service.
        • 📄MoneyDepositedEvent.java
      • 📁exception/ — business-rule violations as typed exceptions (InsufficientFunds, AccountFrozen). Named in business language, extend a domain base exception, no HTTP codes here.
        • 📄InsufficientFundsException.java
      • 📁repository/ PORT — interfaces only, one per aggregate root, speak domain types (save/findById). Implemented in infrastructure.
        • 📄AccountRepository.java
      • 📁port/ PORT — outbound interfaces to the outside world (other contexts, payment rails). Domain says WHAT it needs; an adapter decides HOW.
        • 📄LedgerAccountPort.java
      • 📁service/ ○ optional — stateless domain services: rules that fit no single aggregate (fee calculation). Pure, no Spring.
        • 📄FeeCalculationService.java
    • 📁application/ — use cases. THE ONLY DOOR other contexts may call. Orchestrates; contains no business rules.
      • 📄XxxApplicationService.java — one public method per use case, @Transactional, load aggregate → call verb → save → publish events.
      • 📁command/ ○ optional — input objects for use cases (OpenAccountCommand) when parameters grow past 3–4.
      • 📁result/ ○ optional — read models returned to callers so aggregates never leak out.
      • 📁handler/ ○ optional — event listeners reacting to domain events.
    • 📁infrastructure/ — technical detail. Frameworks live here. Adapters depend on a port, never the reverse.
      • 📁persistence/ — everything database. Owns this context's tables (prefix a_ / c_ / t_ / tr_ / p_).
        • 📁entity/ — JPA entities (@Entity, @Version). Table shape only — NOT the domain model.
          • 📄AccountJpaEntity.java
        • 📁mapper/ — domain ↔ JPA entity translation. No logic beyond copying.
          • 📄AccountMapper.java
        • 📁repository/ — Spring Data interfaces on JPA entities. Package-private to persistence; nothing else touches them.
          • 📄SpringDataAccountRepository.java
        • 📁adapter/ — implements the domain PORT repository: load managed entity, copy state, let dirty-checking UPDATE (Option B).
          • 📄AccountRepositoryAdapter.java
      • 📁ledger/ ACL — adapter calling ANOTHER context's application service, translating its types to ours. The only place allowed to import that context.
        • 📄LedgerAccountAdapter.java
      • 📁rail/ — adapters to external systems (payment rails, banks, gateways). Implements a domain port.
        • 📄AaniAdapter.java
      • 📁config/ ○ optional — @Configuration beans wiring domain services (they have no Spring annotations).
      • 📁reference/ ○ optional — seed / lookup data via plain JPA repos, outside the aggregate.
    • 📁presentation/ — HTTP edge. Translates requests to application-service calls. No business logic, no aggregates in responses.
      • 📁controller/ — @RestControllers: validate input shape, call ONE app-service method, map result to a response.
        • 📄AccountController.java
      • 📁dto/ — request / response records. API contract, separate from domain and JPA types.
        • 📄OpenAccountRequest.java AccountResponse.java
      • 📁exception/ ○ optional — @ControllerAdvice mapping domain exceptions → HTTP status.

      • 📁infrastructure.persistence — read-only, no @Version (config data, not an aggregate)

Flow Direction Balance verbs Entries Status

cashout / settle / release each run in ONE DB transaction — no double-spend. Transaction status guard IS the idempotency check (duplicate settle throws), proven by CashoutRejectAtDispatchTest / TopupDuplicateCallbackTest.

Architecture laws, condensed

  • Layers per context: domain/ (pure JDK, no Spring/JPA) · application/ (use cases, @Transactional, no business rules) · infrastructure/ (persistence, adapters) · presentation/ (controllers, DTOs).
  • Only the Application Service is exposed to other contexts — never the aggregate, domain service, or repository directly.
  • Business verbs, never setters. Events are raised inside the aggregate, pulled and published by the app service.
  • Repository save = Option B: adapter loads the managed JPA entity, copies domain state onto it → dirty checking does the UPDATE, @Version works, domain stays version-free.
  • Tables belong to ONE context, full stop — prefix (a_/c_/t_/tr_/p_) makes ownership visible in the schema itself; other contexts never SELECT them.
  • Idempotency = guarded state transitions on the aggregate (duplicate settle throws), not ifs in a controller.
  • Cross-context calls only through one ACL class per pair (ACL tag above) — keeps the future microservice split a matter of moving a package, not rewriting call sites.
  • Only Application Service and ValueObject are shareable across contexts — Aggregate, Entity, domain Service, Repository never cross a context boundary, not even read-only.
  • Always hexagonal: Ports & Adapters. Domain/Application define PORT interfaces; infrastructure/ supplies adapters (persistence, ledger, rail, pricing). Domain depends on nothing outward — adapters depend on the port, never reverse.
